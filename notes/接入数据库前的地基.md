# 接入数据库前的地基

> 项目：`go-http-service`
> 主题：为什么在写第一行 SQL 之前要先做这六件事，以及每件事解决什么具体问题
> 完成日期：2026-08-22
> 基线：commit `7a70f64` → 分支 `feat/postgres-prerequisites`

---

## 一、为什么不直接开始接数据库

`notes/代码审查问题清单与改进计划.md` 第六节点了一件事：handler 是包级函数，
`SetupRouter()` 不接收任何参数，**拿不到连接池**。这是硬阻塞。

但只解决这一件事是不够的。下面五件事有个共同点：**先做，改动量很小；
等接完数据库再做，要把每个文件重新改一遍。**

| 事项 | 后补的代价 |
|------|-----------|
| 配置集中管理 | `DATABASE_URL`、池大小、连接超时会继续散落在 `main.go` |
| 结构化日志 | 查询失败只有纯文本日志，无法按字段检索；补 slog 要改所有文件 |
| Request ID | 一次请求跨 handler → service → repository → SQL，没 ID 串不起来 |
| 单请求超时 | 慢查询会一直占着 goroutine |
| 就绪探针 | 「进程活着」和「数据库可用」是两件事，混在一起会造成误重启 |

## 二、依赖注入：从包级函数到结构体方法

### 改之前

```go
// internal/handler/health.go
func HealthHandler(c *gin.Context) { ... }     // 包级函数，无状态可持有

// internal/handler/router.go
func SetupRouter() *gin.Engine { ... }         // 不接收任何依赖

// internal/handler/clock.go
var now = func() time.Time { ... }             // 包级可变状态
```

`now` 是包级变量，测试要改它就必须保存再恢复：

```go
func withFixedTime(t *testing.T) {
    original := now
    now = func() time.Time { return fixedTime }
    t.Cleanup(func() { now = original })       // 忘了这行就污染其他测试
}
```

### 改之后

```go
// internal/handler/api.go
type API struct {
    cfg *config.Config
    log *slog.Logger
    now func() time.Time          // 不再是包级变量
    readyChecks []readyCheck
}

func New(cfg *config.Config, log *slog.Logger, opts ...Option) *API

func (a *API) Health(c *gin.Context) { ... }   // 方法，能拿到所有依赖
func SetupRouter(api *API) *gin.Engine
```

测试直接构造一个时钟被钉死的 `API`，不再需要保存/恢复全局状态：

```go
func newTestAPI(opts ...Option) *API {
    base := []Option{WithClock(func() time.Time { return fixedTime })}
    return New(testConfig(), discardLogger(), append(base, opts...)...)
}
```

### 接数据库时怎么用

```go
pool, err := db.Connect(ctx, cfg)
api := handler.New(cfg, logger, handler.WithReadyCheck("database", pool.Ping))
```

`API` 加一个 `pool` 字段即可，路由和其他 handler 一行都不用动。

### Option 模式

`New` 用可变参数的 `Option` 而不是一长串位置参数：

```go
func WithClock(fn func() time.Time) Option
func WithReadyCheck(name string, fn func(context.Context) error) Option
```

好处是加新的可选依赖不会破坏已有调用方。必需依赖（`cfg`、`log`）仍是位置参数，
因为它们缺了服务就跑不起来，编译期报错比运行时空指针好。

## 三、配置集中管理

### 问题

改之前配置散在三处：`main.go` 的 `port()`、`router.go` 的 `trustedProxies()`、
以及两个文件里的常量。

### 关键设计：非法值必须让进程启动失败

```bash
$ PORT=abc go run cmd/server/main.go
server stopped with an error  error="config: PORT must be a number, got \"abc\""
```

**不要静默回退到默认值**。静默回退意味着你以为服务跑在 9000 端口，
实际它在 8080，而且没有任何提示。

### 一次报出所有错误

```go
errs = append(errs, ...)
return nil, errors.Join(errs...)
```

三个配置同时写错，一次全告诉你，不用改一个重启一次。

### 交叉校验

有些约束不是单个值合法就够的：

```go
if c.RequestTimeout >= c.WriteTimeout {
    // 写超时会先触发，handler 的 deadline 永远没机会生效
}
```

> 这条校验在写测试时立刻抓到了我自己写错的测试数据
> （`REQUEST_TIMEOUT=1m` 配 `WRITE_TIMEOUT=25s`）。

## 四、Request ID：一个安全细节

### 基本用途

每个请求分配一个 ID，写进响应头，注入 `c.Request.Context()`，
后续所有日志都带上它，一次请求的所有记录能串起来。

### 客户端传入的 ID 必须校验

支持客户端自带 `X-Request-Id` 是为了跨服务链路追踪。但这个值会被
**原样写进每一条日志**，如果不校验：

```
X-Request-Id: abc\n{"level":"INFO","msg":"payment approved"}
```

客户端就能往你的日志里注入伪造的记录。这叫**日志注入（log injection）**。

校验规则：长度 ≤ 64，且仅含 `[A-Za-z0-9_-]`。不合规就丢弃重新生成。

```go
func sanitiseRequestID(raw string) string {
    if raw == "" || len(raw) > maxRequestIDLen { return "" }
    for _, r := range raw {
        switch {
        case r >= 'a' && r <= 'z', r >= 'A' && r <= 'Z',
             r >= '0' && r <= '9', r == '-', r == '_':
        default:
            return ""
        }
    }
    return raw
}
```

### 生成不需要第三方库

```go
var b [16]byte
rand.Read(b[:])              // crypto/rand
return hex.EncodeToString(b[:])
```

需求只是「不重复」，`crypto/rand` 够了，不必为此引入一个 UUID 包。

## 五、中间件顺序：一个反直觉的决定

```
requestID      →  最先，后续日志才带得上 ID
requestLogger  →  紧随其后，才量得到完整耗时
CustomRecovery →  在 logger 内层  ← 与 gin 常规写法相反
timeout        →  设置 deadline
limitBodySize  →  最后
```

### 为什么 Recovery 不放最外层

常规写法是 `gin.Default()`，Recovery 在最外层。但那样的话：

```
panic 发生
  → 异常穿过 requestLogger 的 c.Next() 向上抛
  → 此刻状态码还没被置为 500
  → Recovery 才捕获并置 500
  → 但 requestLogger 已经错过了
```

访问日志会记成错误的状态码（200 或 0）。

反过来把 Recovery 放在 logger 内层：

```
panic 发生
  → Recovery 捕获，置 500，正常返回
  → requestLogger 读到真实的 500
```

代价是 `requestID` / `requestLogger` 自身 panic 无人兜底，
但这两者逻辑极简，可以接受。测试 `TestRequestLogger_PanicLoggedAs500` 钉住了这个行为。

## 六、单请求超时：只传播 deadline，不写响应

### `http.Server` 的超时管不到 handler

| 超时 | 管的是 |
|------|--------|
| `ReadHeaderTimeout` | 读请求头 |
| `ReadTimeout` | 读完整请求 |
| `WriteTimeout` | 写响应 |
| `IdleTimeout` | keep-alive 空闲 |

它们约束的都是**在 socket 上搬字节**。一个卡在慢查询上的 handler，
上面四项一个都不会打断它。

### 实现

```go
func timeout(d time.Duration) gin.HandlerFunc {
    return func(c *gin.Context) {
        ctx, cancel := context.WithTimeout(c.Request.Context(), d)
        defer cancel()
        c.Request = c.Request.WithContext(ctx)
        c.Next()
    }
}
```

### 为什么不在中间件里写 504

很多教程的超时中间件会起一个 goroutine，超时就抢先写 504。**这是数据竞争**：
handler 可能同时在写同一个 `ResponseWriter`。而且 Go 没有办法强行终止
一个不理会 context 的 handler。

正确的分工是：

- **中间件**：只负责把 deadline 放到 context 上
- **handler**：把 `c.Request.Context()` 传给查询，超时由查询自己返回错误，
  再由 handler 转成响应

所以这条约定必须遵守（已写进 `CLAUDE.md` 4.6）：

```go
// 对
rows, err := pool.Query(c.Request.Context(), sql, args...)

// 错——超时对它完全无效
rows, err := pool.Query(context.Background(), sql, args...)
```

## 七、liveness 与 readiness：用错会放大故障

| | `/api/health` | `/api/ready` |
|---|---|---|
| 回答 | 进程还活着吗 | 现在能处理请求吗 |
| 查依赖 | **否** | 是 |
| 失败后果 | 编排系统**重启**容器 | 编排系统**摘流量**，不重启 |
| K8s 探针 | `livenessProbe` | `readinessProbe` |

### 为什么 health 绝对不能查数据库

如果 `/api/health` 查数据库，那么数据库抖动 3 秒 →
K8s 认为进程死了 → **重启所有 Pod** → 重启期间连接池重建 →
数据库压力更大 → 雪崩。

一个本来只是依赖短暂不可用的问题，被放大成自身的全面故障。

测试 `TestHealthIgnoresFailingDependencies` 钉住了这一点：
即使注册了一个必然失败的检查，`/api/health` 仍返回 200。

### readiness 的三个实现细节

**1. 并发执行**：三个检查各耗 60ms，串行要 180ms。用 goroutine 扇出后按
索引写回结果切片——不同索引不重叠，无需加锁，`-race` 干净。

**2. 保持注册顺序**：结果按索引写入而非按完成顺序追加，响应稳定可 diff。

**3. panic 不能打挂进程**：依赖探针正是那种会在启动期空指针 panic 的代码。

```go
defer func() {
    if r := recover(); r != nil {
        result = model.CheckResult{Status: model.CheckFailed, Error: reasonPanicked}
    }
}()
```

### 检查失败不返回原始错误

```go
// pgx 的连接错误长这样：
// dial 10.0.0.5:5432 refused, user=admin password=hunter2
```

主机、用户名甚至密码都可能在里面。所以只返回三种通用原因
（`check failed` / `check timed out` / `check panicked`），完整错误只写日志。
`name` 字段已经说明是哪个依赖出问题，那才是可操作的信息。

> 这是全项目**唯一**不使用 `ErrorResponse` 的接口：200 和 503 都返回
> `ReadyResponse`。就绪探针由编排系统消费而非 API 客户端，
> 保留检查明细比套用统一错误结构更有价值。

## 九、接 PostgreSQL 时剩下的三件事

```go
// 1. internal/config：加字段
DatabaseURL string   // 复用现有的 envString 助手

// 2. internal/db/db.go：建池
func Connect(ctx context.Context, cfg *config.Config) (*pgxpool.Pool, error)

// 3. cmd/server/main.go：装配
pool, err := db.Connect(ctx, cfg)
if err != nil { return fmt.Errorf("database: %w", err) }
defer pool.Close()        // 位置很重要，见下

api := handler.New(cfg, logger, handler.WithReadyCheck("database", pool.Ping))
```

然后按 `notes/分层架构.md` 建 `internal/repository` 和 `internal/service`。

### 关闭顺序不能颠倒

```
1. 收到 SIGTERM
2. srv.Shutdown(ctx)    先排空在途 HTTP 请求
3. pool.Close()         再关连接池
```

反过来会切断正在执行的查询。实现上靠 defer 的书写位置保证：
`defer pool.Close()` 写在前面（后执行），`srv.Shutdown()` 是普通调用（先执行）。
`main.go` 的注释里写明了这一点。
