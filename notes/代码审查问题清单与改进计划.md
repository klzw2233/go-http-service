## 三、问题清单

### 3.1 严重级（有实际风险，需优先修复）

#### 问题 1：`r.Run()` 的错误被丢弃

**位置**：`cmd/server/main.go:11`

```go
r.Run(":" + port)   // 返回 error，但没有接收
```

**风险**：`Run()` 返回 `error`。当端口被占用、权限不足时，函数返回错误，`main` 随即正常结束，**进程以 exit code 0 静默退出**。运维视角看是"启动成功后立刻退出"，没有任何日志线索。

**修复方向**：至少 `log.Fatal(r.Run(...))`；更好的做法是配合问题 8 一起改成显式 `http.Server`。

---

#### 问题 2：HTTP 服务没有任何超时设置（Slowloris 攻击面）

**位置**：`cmd/server/main.go:11`（间接来自 gin 框架默认行为）

**证据**：gin `v1.12.0` 源码 `gin.go:550`：

```go
server := &http.Server{ // #nosec G112
    Addr:    address,
    Handler: engine.Handler(),
}
```

`ReadTimeout` / `ReadHeaderTimeout` / `WriteTimeout` / `IdleTimeout` **全部是零值，即永不超时**。注意那句 `// #nosec G112` —— 这是 gin 作者主动压制 gosec 的安全告警，G112 的含义正是 "Potential Slowloris Attack"。框架自己承认了这个默认不安全。

**风险**：攻击者只需建立大量连接并极慢地发送请求头，每条连接都会永久占用一个 goroutine 和一个文件描述符，最终耗尽服务资源。这是一种成本极低的拒绝服务手法。

**修复方向**：不使用 `r.Run()`，自建 `http.Server` 并显式设置四个超时。

---

#### 问题 3：请求体没有大小上限

**位置**：`internal/handler/echo.go:15`

```go
if err := c.ShouldBindJSON(&req); err != nil {
```

**风险**：`ShouldBindJSON` 会把整个请求体读入内存后再反序列化。客户端发送一个 1 GB 的 JSON，服务端就会尝试分配 1 GB 内存。少量并发即可打爆进程。

同时 `EchoRequest.Message` 只有 `binding:"required"`，没有长度上限，一个合法的超长字符串同样会被完整回显。

**修复方向**：用 `http.MaxBytesReader` 包裹 `c.Request.Body` 设置硬上限；给 `Message` 加 `max=...` 约束。

---

#### 问题 4：错误响应泄露 Go 内部类型名

**位置**：`internal/handler/echo.go:16-18`

```go
c.JSON(http.StatusBadRequest, gin.H{"error": err.Error()})
```

**证据**：实际发送三种坏请求，得到的真实响应：

| 请求体 | 状态码 | 响应体 |
|--------|--------|--------|
| `{}` | 400 | `{"error":"Key: 'EchoRequest.Message' Error:Field validation for 'Message' failed on the 'required' tag"}` |
| `{"message":` | 400 | `{"error":"unexpected EOF"}` |
| `{"message":123}` | 400 | `{"error":"json: cannot unmarshal number into Go struct field EchoRequest.message of type string"}` |

**问题有两层**：

1. **信息泄露**：内部结构体名 `EchoRequest` 直接进入公开 API 响应。攻击者据此可以推断服务端的技术栈（Go + go-playground/validator）和内部数据结构。
2. **契约不稳定**：三条错误的措辞、结构完全不同，且会随着依赖库版本升级而变化。客户端无法程序化处理，只能拿去展示给用户看 —— 而这些英文技术术语对终端用户毫无意义。

**修复方向**：定义统一的错误响应模型，返回稳定的错误码 + 人类可读信息，原始错误只写日志不返回。

---

### 3.2 中等级（架构债，迟早要还）

#### 问题 5：404 返回纯文本，与 JSON API 契约不一致

**证据**：实测 `GET /api/nope` → `404`，响应体 `404 page not found`，`Content-Type: text/plain`。

**风险**：客户端对所有响应统一按 JSON 解析时，这里会解析失败，暴露成一个"未知错误"而非清晰的 404。

**修复方向**：`r.NoRoute()` 注册 JSON 格式的兜底处理器。

---

#### 问题 6：405 未启用，方法错误被误报为 404

**证据**：实测 `GET /api/echo`（该路由只注册了 POST）返回的是 **404**，而不是 405。

**原因**：gin 的 `Engine.HandleMethodNotAllowed` 默认为 `false`。

**风险**：调用方拿到 404 会以为"接口不存在"，从而去排查路由配置、部署版本，而真实原因只是 HTTP 方法用错了。这是一类非常浪费时间的误导性错误。

**修复方向**：开启 `HandleMethodNotAllowed`，并注册 `r.NoMethod()`。

---

#### 问题 7：端口硬编码

**位置**：`cmd/server/main.go:8`

```go
port := "8080"
```

**风险**：容器化部署（路线图第 5 步）时端口必须可注入。硬编码意味着换端口要重新编译。

**修复方向**：读 `os.Getenv("PORT")`，未设置时回退到 `8080`。

---

#### 问题 8：没有优雅关闭

**风险**：进程收到 `SIGTERM` 时立即死亡，**在途请求被直接切断**。K8s 滚动更新（路线图第 6 步）每次都会产生一批 5xx。

更关键的是：接入 PostgreSQL（路线图第 2 步）之后，没有优雅关闭就意味着连接池不会被正常释放。**所以这一项必须在接数据库之前做完。**

**修复方向**：`signal.NotifyContext` 监听 `SIGINT` / `SIGTERM`，配合 `srv.Shutdown(ctx)` 做带超时的排空。

---

#### 问题 9：版本号硬编码且重复

**位置**：`internal/handler/health.go:22` 与 `internal/handler/handler_test.go:37`

```go
Version: "0.2.0",                                       // health.go
assert.Contains(t, resp.Body.String(), `"version":"0.2.0"`)  // handler_test.go
```

**风险**：改一次版本要动两个文件，漏改一处则测试红或者接口返回错版本。同理 `Name: "go-http-service"` 也是散落的字面量。

**修复方向**：提取为包级常量；进一步可用 `-ldflags -X` 在构建时注入真实版本与 commit hash。

---

#### 问题 10：从未调用 `SetTrustedProxies`，客户端 IP 可伪造

**证据**：gin 启动时会打印告警（源码 `gin.go:543-546`）：

```
[WARNING] You trusted all proxies, this is NOT safe.
```

**风险**：gin 默认信任所有代理，`c.ClientIP()` 会直接采信请求头里的 `X-Forwarded-For`，而该头部完全由客户端控制。

当前没有 handler 使用 `ClientIP()`，所以暂无实际危害。**但路线图里的日志模块和限流中间件一旦上线就会中招** —— 限流按 IP 计数，而 IP 可伪造，等于限流失效。

**修复方向**：显式 `r.SetTrustedProxies(...)`，只信任真实的反向代理地址；无代理时传 `nil`。

---

#### 问题 11：成功响应用类型化模型，错误响应用裸 `gin.H`

**位置**：`internal/handler/echo.go:16`

**风险**：成功路径返回 `model.EchoResponse`（有类型、有 JSON tag、可被测试反序列化），错误路径返回 `gin.H{...}`（临时 map，无契约、无法复用）。两套风格并存，错误格式会随手写随手变。

**修复方向**：定义 `model.ErrorResponse`，全项目错误响应统一走它。

**证据**：


### 为什么是这个顺序

**第 2 步排最前**：换行符问题成本只有几分钟，但它污染每一次 `git status` 和 `git diff`。不先解决，后续每个提交都会混入无关的空白改动，review 会非常痛苦。

**第 3 步紧随其后**：问题 1、2、7、8 全部集中在 `main.go`，是同一次改造的自然产物 —— 把 `r.Run()` 换成显式 `http.Server` 时，超时、错误处理、优雅关闭本来就是一起写的。

**第 3 步必须早于接入 PostgreSQL**：优雅关闭是释放数据库连接池的前提（见问题 8）。地基不打好就加数据库，后面要返工。

**第 7、8 步垫后**：测试重构和 CI 属于质量保障，它们应该在被保障的代码稳定之后再动，否则要跟着改两遍。

## 六、本次未做、但建议在接数据库之前处理的事

以下几项在审查中发现，但**不属于「修 bug」而属于「架构决策」**，需要人来定方向，
所以没有直接改，留在这里作为下一步的输入。

### 6.1 handler 需要依赖注入（优先级最高）

当前三个 handler 都是包级函数，没有任何状态：

```go
func HealthHandler(c *gin.Context) { ... }
```

`SetupRouter()` 也不接收任何依赖。这在没有外部依赖时没问题，但**下一步接
PostgreSQL 时必然要改**：handler 需要拿到数据库连接池，之后还有日志器、配置对象。

届时的常见做法是把 handler 变成结构体的方法：

```go
type API struct {
    db  *pgxpool.Pool
    log *slog.Logger
    now func() time.Time
}

func New(db *pgxpool.Pool, log *slog.Logger) *API { ... }
func (a *API) Health(c *gin.Context) { ... }

func SetupRouter(api *API) *gin.Engine { ... }
```

本次第 6 步引入的包级 `now` 变量是**过渡方案**：它解决了时间不可测的问题，
代价是引入了包级可变状态（所以测试里用 `withFixedTime` 显式保存和恢复）。
一旦改成结构体，`now` 应该收进 `API` 字段，包级变量随之删除。

**建议在接 PostgreSQL 的同一个改动里一起做**，而不是先接数据库再重构。

### 6.2 日志还是 `log` 标准库

`main.go`、`errors.go`、`router.go` 里用的都是标准库 `log`，输出是非结构化的纯文本。
路线图第 4 步会引入日志模块，届时建议：

- 换成 `log/slog`（Go 1.21+ 标准库，无需第三方依赖）
- 加一个 request ID 中间件，把 ID 注入 context，让一次请求的所有日志可以串起来
- 把 gin 的 `Logger()` 换成基于 slog 的自定义中间件，输出 JSON 格式

### 6.3 缺少的中间件

目前只有 `Logger`、`CustomRecovery`、`limitBodySize` 三个。接口对外之前还需要：

| 中间件 | 用途 | 备注 |
|--------|------|------|
| 请求超时 | 单个请求的处理时长上限 | `http.Server` 的超时管不到 handler 内部的慢查询 |
| Request ID | 日志串联、问题排查 | 见 6.2 |
| CORS | 浏览器跨域访问 | 有前端时才需要 |
| 限流 | 防滥用 | 依赖第 10 项已修好的真实客户端 IP |
| 安全响应头 | `X-Content-Type-Options` 等 | 对外暴露时补 |

### 6.4 可以考虑的加固项

- **`DisallowUnknownFields`**：目前请求体里的未知字段会被静默忽略
  （已有测试记录该行为）。若希望拼错字段名时报错而不是静默丢弃，可以开启。
  这是产品决策，不是 bug。
- **`govulncheck`**：加进 CI 可以自动检查依赖的已知漏洞，一步的成本。
- **健康检查分级**：接数据库后，`/api/health` 应该区分「进程活着」（liveness）
  和「依赖可用」（readiness），K8s 需要这两个不同的探针。
